# Better Auth evaluation

Evaluated October 13, 2026 against the current working tree and upstream documentation/source. This records the original architectural evaluation. The subsequent implementation pins Better Auth 1.7.7 and uses Cloudflare Email Service from bot@okener.com; see the README for current setup, migration, and rollout requirements. The domain owner reports that Email Service onboarding is complete; production delivery still needs verification.

**Recommendation: replace the custom credential/session implementation with Better Auth before the account feature's production rollout.** Keep the game storage, ownership checks, autosave, publication, and daily scoring code. Prefer real email/password accounts with username sign-in and verified-email recovery. Preserving username-only accounts and standalone recovery codes is possible only with additional design/customization; it reduces the maintenance benefit.

| Area | Current implementation | Assessment |
| --- | --- | --- |
| Runtime and storage | Request/Response Worker, D1, `nodejs_compat` | Good architectural fit: Better Auth supports a native D1 binding. No ORM, framework migration, separate auth service, or third-party Cloudflare plugin is necessary. |
| Browser | Plain JavaScript ES modules copied into a generated Worker | Keep the UI. Use documented HTTP endpoints or bundle the vanilla client; bare npm imports cannot be served by the current browser build. |
| Credentials | Custom username/password routes and native scrypt | Move credential handling to Better Auth. Its standard username plugin adds username login to email/password authentication; signup still requires email. |
| Recovery | One-time random recovery code, no email | Recommend verification and reset emails. An email delivery implementation and sender setup are new operational dependencies. |
| Sessions | D1 rows, hashed tokens, 30-day HttpOnly cookies | Replace session resolution with Better Auth's server API; explicitly configure expiry and revocation behavior. Existing cookies should be invalidated at cutover. |
| Application data | `account_id` ownership, daily identity and claims | Remain application responsibilities. Preserve user IDs and server-side checks. Better Auth does not provide cloud game sync or daily scoring. |

Native D1 support, including D1 batch operations, is documented in the [1.5 release notes](https://better-auth.com/blog/1-5). The [installation guide](https://better-auth.com/docs/installation) documents standard HTTP handlers, vanilla JavaScript support, the auth secret and base URL. Current documentation identifies version 1.7.7; implementation should pin and verify the selected release rather than install an unreviewed moving target.

The [username plugin](https://better-auth.com/docs/plugins/username) documents email as a required signup field. Keep public display name separate from email. Do not generate pretend email addresses: they would leave recovery unusable and complicate future account linking. If email-free signup is a firm requirement, evaluate that explicitly before committing to this recommendation.

The [password documentation](https://better-auth.com/docs/authentication/email-password) supports custom password verification, email reset delivery, and session revocation after reset. Explicitly enable `revokeSessionsOnPasswordReset`; it is not the documented default. Our current hash format is `scrypt$salt$hex` with N=16384, r=8, p=5. Sharing an algorithm does not make hashes interchangeable. Any populated migration must test an exact legacy-format verifier rather than copying hashes into a default verifier and assuming compatibility.

One storage difference deserves an explicit decision: our `auth.mjs` stores only SHA-256 session-token hashes. Better Auth 1.7.7's [internal adapter source](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/better-auth/src/db/internal-adapter.ts) creates a token and persists/queries that token in the session model. Do not describe adoption as retaining our hashed-session-storage property. This observation does not imply that a database token alone bypasses its cookie protections.

Proposed integration:

1. Add a server-only Better Auth factory using the Worker D1 binding, an explicit base URL/trusted origins, a high-entropy Worker secret, email/password, and the username plugin. Preserve the 15-character password minimum. Mount its handler at `/api/auth/*`.
2. Give Better Auth its own clearly named user, session, credential/provider, verification, and rate-limit tables. Its “account” model means a credential/provider relationship, while our `accounts` table currently means a person; these are different models. Generate reviewed SQL into the existing D1 migration sequence, not runtime automatic production migrations.
3. Change `resolveAccount` to call the server-side session API and return the application's existing `{ id, username, name }` shape. Use stable UUID user IDs. Provision the corresponding daily player idempotently; do not depend on a signup hook having completed every application-side write.
4. Retarget the four application ownership foreign keys (`account_games`, `daily_players`, `daily_claims`, and `games`) to the chosen Better Auth user table while preserving IDs and all records. Remove the custom signup/login/session/recovery routes after cutover. Do not retain an alternate custom authentication path indefinitely.
5. Update the account dialog for email, verification and password-reset screens. Preserve guest play, local imports, explicit guest-history claims, account-change detection across tabs, and autosave/conflict behavior. Keep the server auth module outside the browser import graph: the local room preview currently imports `api.mjs` in the browser.
6. Configure database-backed limits and Cloudflare's trusted client IP header. Verify whether the selected release's limits cover our existing per-username protection as well as per-IP rules. Initially leave cookie caching disabled so logout and reset revocation can be verified directly. These are implementation choices, not claims that defaults match our current policy.

[Rate-limit documentation](https://better-auth.com/docs/concepts/rate-limit) explains that the default store is memory and offers database storage and `cf-connecting-ip` configuration. [Session documentation](https://better-auth.com/docs/concepts/session-management) describes the server session API and cookie caching. Use those supported extension points before considering extra infrastructure.

Migration depends on actual deployment state. The last recorded rollout status in this chat was “not deployed”; this evaluation did not query production. If there are no real custom-auth accounts, avoid a legacy-password bridge. If accounts do exist, preserve IDs, prove ownership before enrolling an email, migrate credentials through a tested verifier or a controlled reset/enrollment flow, and force reauthentication. Existing recovery codes are not automatically Better Auth reset tokens. Do not rewrite a migration that has already been applied anywhere; use a forward migration and rehearse rollback/data recovery.

Before rollout, prove the selected package bundles and runs under the existing `cf`/Wrangler build, measure signup/login CPU time and bundle size, and apply generated migrations to an isolated D1 database. Exercise verification and recovery with a test mail transport. Preserve the existing game/daily tests and add end-to-end signup, username login, cross-device sessions, logout/reset revocation, cross-origin rejection, distributed throttling, migration data preservation, and concurrent daily-player provisioning tests. Inspect upstream [security advisories](https://github.com/better-auth/better-auth/security/advisories) when pinning/upgrading. No such runtime spike was performed for this evaluation, so bundle/CPU behavior remains unverified.

This is a moderate auth/schema/UI refactor with a useful reduction in bespoke security-sensitive code. It introduces package updates, an auth secret, and email operations; it does not eliminate application authorization or security maintenance.
